Data Models & MDF

Employee Central data is defined by data models (XML, maintained mostly through UIs today) and by the Metadata Framework (MDF) for generic objects.

Quiz this topic

Key concepts

  • Succession Data Model. Defines person and employment HRIS elements such as personalInfo, jobInfo and compInfo, their fields, labels and visibility.
  • Country/Region-specific Succession Data Model. Adds country-specific fields and formats, e.g. a German home address format or local personal data fields.
  • Corporate Data Model. Defines legacy (non-MDF) foundation objects. Its country/region-specific variant adds local fields to them.
  • Manage Business Configuration (BCUI). The Admin Center UI to maintain HRIS elements and fields of the Succession Data Model, including labels, visibility, required flags and rule assignments, without editing XML.
  • Field attributes. visibility is none, view or edit. Whether a field is mandatory is a separate required attribute. Permissions still decide what a given user sees.
  • MDF basics. Configure Object Definitions defines the structure of an object. Manage Data creates and edits records. Custom objects and fields get the prefix cust_.
  • Effective dating. MDF objects can be not effective dated, effective dated, or take their dating From Parent (used for children in a composite association).
  • Associations. A composite association makes the child part of the parent: created, edited and deleted together. A valid-when association links two independent objects, e.g. to filter values.

Common traps

  • mandatory is not a visibility value.
  • Defining an object (Configure Object Definitions) and maintaining its records (Manage Data) are different tools.
  • Country-specific employee fields go into the country-specific Succession data model, not the Corporate one.

Practice tasks

Do these in a practice or demo instance. Each one ends with how to prove the outcome, just like in the exam.

A new field on Job Information

Outcome: Job Information has a new custom text field Shift Group that is editable and optional.

Hints
  1. Open Manage Business Configuration and the jobInfo element.
  2. Enable an unused custom-string field, set its label, visibility and required flag.

Prove it: Open an employee's Job Information edit screen and show the new field. If you can't see it, check permissions next.

Parent-child MDF object

Outcome: A custom object Training Plan exists with a child object Training Item that is maintained inside each plan.

Hints
  1. Create the child object first with effective dating From Parent.
  2. Create the parent with a composite association to the child.
  3. Secure both if HR must permission them.

Prove it: In Manage Data, create one plan with two items, then show that both items are part of the plan record.

Country-specific personal data

Outcome: A field that only exists for employees in one country appears in Personal Information for that country.

Hints
  1. Look at the country/region-specific configuration of personalInfo in BCUI.

Prove it: Compare the Personal Information screen of an employee in that country with one elsewhere.
